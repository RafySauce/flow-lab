# Decision Log — 2026-08-21 — Bug Root Cause and App Code Fields

**What was decided:** add `app_code` and `root_cause` to `bug` as required
custom fields, on top of the existing `summary` + `description` +
`customer_business_value` + `acceptance_criteria` + `type_of_work` +
`work_category` + `due_date` set — every bug this flow generates must state
which application it affects and why the defect occurs, with no exception.
**By whom:** agent, on direct operator instruction. **What it affects:**
`reference/work-item-schemas.md` (1.7 → 1.8), Stage 04 `CONTEXT.md` (1.6 →
1.7), Stage 05 `CONTEXT.md` (1.7 → 1.8), Stage 06 `CONTEXT.md` (1.11 → 1.12),
`reference/on-engine-validation-checklist.md` (1.3 → 1.4), the
`field-refinement-cadence` (1.5 → 1.6) and `jira-commit` (1.11 → 1.12) skill
specs and both skills' adapters, and `HUB.md` (1.24 → 1.25).

## The feedback

> "we need to make sure that anytime a bug work item type is generated by the
> ai refinement flow that the root cause and app code fields are filled in."

## Decisions and alternatives

1. **`app_code` and `root_cause` become separate required schema fields, not
   additional prose folded into `description`.** The 2026-07-07 simplification
   (see the related decision log) deliberately narrowed `bug` to three fields
   by folding reproduction steps, expected/actual result, severity, and
   environment into `description`'s content — but that field's content rule
   (Extension field definitions in `work-item-schemas.md`) is already fully
   occupied by the reproduction/expected/actual contradiction requirement.
   Layering "which application" and "why it happens" onto the same field
   would recreate the ambiguity that simplification was written to remove,
   and neither concept is close in kind to what `description` already holds:
   `description` states *what was observed*; `app_code` and `root_cause` are
   *routing* and *diagnosis* concerns, the same kind of distinct classifier
   `type_of_work`/`work_category` already are for board workflow (rule 5,
   `work-item-schemas.md`). Two new fields, not a longer paragraph, is the
   more consistent shape. *Alternative considered:* append a "root cause"
   and "affected application" paragraph inside `description`, keeping `bug`
   at three fields — rejected because it reopens exactly the field-boundary
   ambiguity 2026-07-07 was written to close, and because `app_code` is
   naturally a short, structured value (a code, not prose), which fits a
   dedicated field far better than free text inside a narrative block.
2. **`app_code` reuses an existing flowspace concept rather than inventing a
   new taxonomy.** Stage 01's supporting-context research step already asks
   the user for "app/system codes" as a search-term filter
   (`ai-refinement-hybrid.md`'s `supporting_context_research` amendment,
   transcribed in `HUB.md`'s "Supporting-context research" section). `bug`'s
   `app_code` field names the same kind of value — this keeps one convention
   for "which application" across the flowspace instead of two.
3. **`root_cause`'s content rule allows an explicit "not yet confirmed"
   statement, but never a blank field or a confident-sounding fabrication.**
   Bugs are frequently filed before root cause is actually isolated, so a
   hard requirement for a *confirmed* cause would either block routine bug
   creation or invite the agent to guess convincingly and call it settled —
   both worse than the alternative. The rule instead requires the field to
   state either a concrete causal mechanism distinct from the symptom already
   in `description`, or an explicit statement that the cause is unconfirmed
   plus what is suspected. This mirrors the flowspace's existing
   anti-fabrication discipline (bulk mode's "report underspecified rather
   than pad" rule, `due_date_elicitation`'s "never infer, always elicit"
   rule) applied to a new field rather than inventing a new principle.
4. **Field order places `description` immediately after `summary`, then
   `app_code`, then `root_cause`, ahead of `customer_business_value`.**
   `root_cause` is drafted against the reproduction/expected/actual content
   `description` establishes — it cannot be confidently drafted before that
   content is confirmed, so `field-refinement-cadence`'s dependency-ordering
   rule (Method step 1) places it after `description`. `app_code` has no such
   dependency and could in principle sit anywhere, but grouping it with
   `description` and `root_cause` keeps the bug-specific block contiguous
   rather than scattered through the field walk.
5. **Both fields are added to `field-refinement-cadence`'s conflict-detection
   step, not left to completeness alone.** A required field that is merely
   non-empty can still be wrong — `root_cause` could name a cause that
   doesn't match the actual result `description` states. Method step 3 gains
   a cross-field check (root_cause consistent with description's actual
   result) alongside the existing within-field description check, plus an
   explicit non-empty check on both new fields, so a drafted-but-inconsistent
   value is caught before Stage 05 rather than only at completeness scan.
6. **`jira-commit` discovers both as ordinary custom fields, same
   ADF → plain-text → description-fallback testing as every other bug or
   type-level custom field.** No special-casing: the `commit_boundary_
   hardening` house amendment's field-capability testing and the post-commit
   field audit (Stage 06 step 7b / `jira-commit` Method step 4a) already
   apply generically per schema-required field, so both new fields are
   caught by the existing re-fetch-and-verify mechanism without a bespoke
   check — this is precisely the gap-catching machinery the operator's
   instruction ("make sure ... filled in") calls for, applied to two more
   fields rather than requiring new machinery.

## Assumptions (operator to confirm or amend)

- **E1 — `app_code` and `root_cause` are Jira custom fields the target
  project must have or create, same as `type_of_work`/`work_category` and
  spike's `question_to_answer`/`timebox`.** Neither has been confirmed
  against a real Jira project's field configuration; per the registry's
  "Hierarchy levels and field capability" cross-cutting note, Stage 06 tests
  each field's actual accepted format at commit time rather than assuming it,
  and a field the target instance lacks entirely is a named halt, not a
  silent drop. This is the same to-review posture every other house-extension
  field in this registry already carries.
- **E2 — `root_cause`'s "unconfirmed, but state what's suspected" allowance
  is a judgment call, not an explicit operator instruction.** The operator's
  feedback said the field must be "filled in," not how to handle a bug
  reported before root-cause analysis is possible. The alternative — treating
  an unconfirmed root cause the same as bulk mode's underspecified-item
  handling (report the gap, don't create the item) — would block routine bug
  intake until an investigation completes, which reads as a worse outcome
  than requiring an honest "not yet isolated, suspect X" statement. Flagged
  for the operator to override if a stricter gate (no commit until root
  cause is confirmed) is actually intended.
